## 二、技术选型规律

1. **存储两极分化**：个人向项目清一色 **SQLite 单文件**（Memos/Joplin/Trilium/SiYuan）；团队向项目用 Postgres+Redis（Outline/Docmost）。个人知识库选 SQLite 是被反复验证的正确答案。
2. **编辑器是重量分水岭**：Tiptap/ProseMirror/BlockSuite（重，协作强、成本高）vs Markdown 纯文本（轻，互通性好）。个人场景后者性价比更高。
3. **搜索是最常见的短板**：Outline 依赖 PG FTS（中文弱）、Memos/Joplin 的 SQLite FTS 中文分词差、SiYuan 自建索引。**中文检索是自研项目最容易做出差异的点**。
4. **同步/协作是复杂度爆炸点**：Yjs/CRDT（AFFiNE/Outline/Docmost）带来 correctness 红利也带来架构包袱；Logseq 的 DB 版重构长期 beta 即是教训。

## 四、九项目教训（反面清单）

| 教训 | 案例 | 简知的对策 |
|---|---|---|
| 部署件套越多，自托管采用率越低 | Outline 需 PG+Redis+S3+OIDC | 零外部依赖，`node index.js` 即起 |
| 资源占用失控劝退用户 | AFFiNE 社区反馈内存泄漏 | 纯服务端渲染字符串，无常驻重进程 |
| 数据格式封闭造成迁移恐惧 | SiYuan .sy / Logseq DB 版断代 | 存储即开放 SQLite + 一键 JSON 全量导出 |
| 中文搜索长期敷衍 | Memos/Joplin 社区长期 issue | LIKE 子串匹配开箱即用，FTS5 trigram 备好升级路径 |
| 大重构拖垮主线 | Logseq DB 版长期 beta | 小内核 + 数据层集中（单文件 db.js），可整体替换 |
| 上手门槛高 | Trilium 概念繁多 | 三栏直觉布局 + 首启引导笔记 |

## 五、对简知的直接启示（已吸收）

1. **Memos**：最小数据模型 + 单容器零门槛部署 + API 优先 → 单命令启动、REST 完整、种子引导。
2. **Trilium**：树/克隆/链接混合组织、属性元数据层 → v0.1 先做双链，标签即元数据，层级列入路线图。
3. **Joplin**：同步目标抽象层 + E2EE → v0.1 不做同步，但存储层集中在 db.js 为未来留出替换点。
4. **SiYuan**：明文为真相源 + 可重建索引 → 内容存 SQLite 单文件 + 每次写入维护 search_text。
5. **Outline**：不引 ES、用主库扛全文检索 → 同哲学：LIKE 起步，FTS5 trigram 是同库内的下一步。
6. **Logseq**：Journal 输入流降低记录摩擦 → 挖掘为 v0.2 候选（每日笔记）。
7. **BookStack**：克制的产品边界哲学 → 非目标清单（多用户/协作/同步）写进 PRD，防止范围膨胀。

## 六、简知的差异化定位

在「**轻量零依赖** × **中文检索友好** × **双链知识网** × **数据完全自主**」四个维度的交集上，现有开源项目没有同时做好的方案——这就是简知的立足点。
