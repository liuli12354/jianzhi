# 简知（JianZhi）· 技术方案

> 2026-09-13 ｜ 决策依据：`docs/research/` 九项目调研 + 本机环境实测（Node 22.23.2 / win32 x64）

## 1. 选型总览（每项附调研依据）

| 层 | 选型 | 理由（对照调研结论） |
|---|---|---|
| 后端 | Node.js 22 + Express 5 | 与前端同语言；个人规模性能充裕；Express 5 为当前安装默认主版本（SPA 通配路由需按新语法写，见 §5） |
| 存储 | SQLite（better-sqlite3 v13，WAL 模式） | Memos/Joplin/Trilium 三个不同形态的项目共同验证：**单文件零运维是个人知识库的最优存储解**；同步 API 免去连接池管理 |
| 前端 | React 18 + Vite 8 + TypeScript（strict） | 纯 SPA 无 SSR 需求，Vite 构建秒级；严格类型保证重构安全 |
| Markdown | marked + DOMPurify + 自研 ~50 行极简高亮 | 编辑器选型上 Outline/Docmost 的 Tiptap/ProseMirror 对 v0.1 明显过重；DOMPurify 防存储型 XSS；highlight.js 因供应链安全钩子拦截改为内置实现（收益：零依赖） |
| 搜索 | `search_text` 冗余列 + LIKE 子串匹配 | 直接规避 Memos/Joplin 的中文 FTS 痛点：中文无需分词即可子串命中；万条以内全表扫描毫秒级；FTS5+trigram 列为 v0.2 升级项 |
| 部署 | `node index.js` 一条命令；生产模式同源托管 `web/dist` | 对标 Memos 的"单容器"体验；对比 Outline 必须的 PG+Redis+S3+OIDC 四件套，本方案**零外部依赖** |

## 2. 架构

```
浏览器 SPA (React)
   │  /api/*  REST JSON
   ▼
Express (app/server)
   ├── 路由层 src/app.js（校验/编排，无 SQL）
   ├── 数据层 src/db.js（全部 SQL 集中于此，可替换存储实现）
   └── SQLite 单文件  app/data/jianzhi.db（WAL）
   
生产模式：Express 同时静态托管 app/web/dist（同源，无 CORS/代理问题）
开发模式：Vite dev server 5173 代理 /api → 4321
```

## 3. 数据模型（5 张表）

```
notebooks(id, name, icon, sort_order, created_at, updated_at)
notes(id, notebook_id→notebooks ON DELETE SET NULL, title, content,
      pinned, starred, search_text, created_at, updated_at, deleted_at)
tags(id, name UNIQUE)
note_tags(note_id→notes CASCADE, tag_id→tags CASCADE, PK(note_id,tag_id))
versions(id, note_id→notes CASCADE, title, content, created_at)
索引：notes(notebook_id)、notes(deleted_at)、versions(note_id)
```

- `search_text = (title + '\n' + content).toLowerCase()`，写入时维护，检索免函数计算。
- 软删除：`deleted_at` 置时间戳；彻底删除才物理 DELETE（级联清理 versions/note_tags）。

## 5. 关键设计决策

1. **中文搜索走 LIKE 而非 FTS**（调研驱动）：unicode61 分词器对 CJK 不友好是 Memos/Joplin 的社区痛点；个人数据量（<1 万条）下 LIKE 子串是最朴素且完全正确的方案；schema 不做任何改动即可平滑升级 FTS5 trigram。
2. **版本快照的触发条件**：仅当标题或内容实际变化时写入 versions（防抖保存不会产生垃圾版本），每篇保留最近 20 版，恢复操作本身也会先快照当前态（可无损撤回）。
3. **双链实现**：内容中 `[[标题]]`（支持 `[[标题|别名]]`）；后端用小写化后的 search_text 做 LIKE 匹配实现反链查询；前端在 marked 渲染后的 HTML 上做后处理（跳过 `<pre>/<code>` 片段）生成带 data-target 的锚点，DOMPurify 放行该属性，点击走事件委托 → `/api/resolve` 按标题跳转。
4. **Express 5 兼容**：5.x 的 path-to-regexp v8 不再支持 `app.get('*')`，SPA 回退改用无路径中间件判断 method+path 前缀。
5. **安全边界**：所有富文本渲染经 DOMPurify 消毒；SQL 全部参数化；无鉴权（v0.1 仅限本机/内网，公网部署需加反代认证）；项目零硬编码凭据。
6. **测试策略**：数据层 + HTTP 全走真实 SQLite（临时目录）与原生 fetch，13 个集成用例覆盖主流程与边界；Windows 下 `node --test <dir>` 有目录解析问题，测试脚本直接指向文件。

## 7. 风险与后续路线

| 风险 | 缓解 / 路线 |
|---|---|
| LIKE 全表扫描随数据量退化 | v0.2 升级 FTS5 trigram（SQLite 内建，对中文友好），schema 无需变更 |
| 无鉴权不能暴露公网 | 文档注明仅限本机/内网；公网需反代加 BasicAuth/Token |
| 大文档渲染性能 | 远期：预览分页/虚拟化；当前个人规模无感 |
| highlight.js 缺位 | 内置极简高亮覆盖注释/字符串/数字/关键字；复杂语言高亮列回 P1 |
